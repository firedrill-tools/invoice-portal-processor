# Qualified invoice portal runtime

## Native SDK and completion

Node 22+, `@anthropic-ai/sdk` 0.134.0 and Playwright 1.64.1 are locked. Normal CLI execution constructs a per-run Messages client with an explicit enabled model/key, validated provider base URL, `authToken:null`, `webhookKey:null`, no SDK retry and no global client/config mutation. Version changes need requalification. An optional injected client retains caller options/resources; its returned observations are labeled client reports with no invented raw HTTP evidence.

The public SDK fetch seam persists prepared request JSON before dispatch and original decoded response bytes/body/hash, HTTP/request/message/model IDs, unknown fields, independent usage and failures before returning a reconstructed response to the SDK. Authorization headers are excluded. Only the known bounded JSON Messages path/output/tool declaration is allowed. Original completion validates every block/call before any browser action: tool_use for supported calls, nonblank end_turn without pending calls for success. Thinking/redacted metadata remains supported; incomplete/refused/paused/absent/mismatched metadata, malformed/oversized/nonfinite JSON, unsupported calls/arguments and replayed IDs fail. The parsed SDK result is checked again independently.

All prepared native attempts participate in each independent input/output/cache-creation/cache-read/optional-total aggregate. Absent, partial or invalid counters stay unknown; explicit zero remains zero. Totals and cache semantics are not reconstructed by addition. Original independent total99 remains99. Failed HTTP503 input7 is retained even when the SDK has no returned usage; the sample after ten input10/output5 responses records original107/50, while SDK reports include an unknown failed attempt. Cost remains null. Raw provider bodies and SDK/caller observations are separate evidence.

## Browser and effect authority

A fresh context is owned through public Chromium launchServer/connect APIs. Startup failures and parent cancellation close context/connection/server; actual child-process exit is checked. Late resource completion registers cleanup without later receipt mutation. Close faults fail the run even if the process has exited. Caller-injected launch doubles are test seams, separately qualified from real Chromium paths.

The configured portal is exactly a loopback HTTP root (127.0.0.1/localhost/IPv6 loopback) without credentials/query/fragment. Browser HTTP resources/navigation/forms are intercepted before dispatch, constrained to exact origin and owned page, with unsupported methods blocked. Service workers are disabled. An explicit current submit button grants one matching invoice POST; its prepared form bytes/hash are recorded first. Redirect/resource origin violations stop work. This qualifies this local application's HTTP behavior; it is not an OS network sandbox. The inherited remote font import was blocked in the real browser and removed; local font fallbacks need no external resource.

The server still owns approval, source-value, arithmetic, revision and duplicate checks in Store.submit. A query parameter cannot confirm a nonexistent entry. New canonical safe entry IDs advance from maximum prior identity. Original POST303 entry/source/replay headers identify acknowledged commits; a failed or missing acknowledgement is retained as uncertain and cannot produce a successful run result. Observed added/changed/removed entry IDs remain separate from those browser-acknowledged effects, including unrelated human writes. Provider failure, cancellation, recording error or unavailable final source cannot erase a known acknowledged entry. Fresh readback of an existing entry produces no new effect. The CLI exposes entry_recorded/no_new_entry from acknowledged effects and includes known committed IDs on failures. Full reviewed-source/original-request replay and cooperating writer correctness are separate pending state work.

## Ownership, bounds and private records

The owner aborts new operations at a configurable deadline up to 120 seconds, clears its timer/parent listener and closes browser resources. Provider HTTP 15 seconds; portal read 5 seconds; browser actions/navigation 5 seconds and startup 10 seconds. Each browser close step has 5 seconds, with bounded kill fallback; final source audit has its own 5 second cleanup budget. Filesystem flush/publication is awaited, so these are dispatch/operation bounds rather than a hard total wall-clock promise. Node's global fetch pool and an injected caller's connections remain their owners' resources; only owned operations/signals/readers are stopped.

Limits are 18 prepared provider requests/rounds, 1800 requested output tokens, 32 calls/message and 128 accepted tool calls, 1 MiB provider request/retained decoded response, 129 observations, 4 MiB retained viewport PNG, 6000 page-text characters and 40 controls (2000 characters/value). Form intent is capped at 16 KiB; input task at 2000 characters. Capture limits do not establish compressed-wire traffic, peak heap or billing limits.

Each run directory is newly 0700 and trace/PNG files 0600; existing parents retain their modes. Unique staged files flush before atomic replacement and parent sync. Receipts bind task/instruction/source hashes, initial/final portal facts, original HTTP and SDK/client reports, prepared actions/results, browser HTTP intent/acknowledgements and lifecycle/effects. Screenshots are real viewport captures with hashes. Source API snapshots currently qualify basic shape, not the full pending business schema.

Recording failures latch and prevent subsequent actions. Native in-flight operations and browser evidence queues drain before final publication; cancellation during a delayed original-response write leaves a stable final receipt. Failed receipts retain actual effects and errors; final storage failure gets a best-effort failed write. If publication cannot be confirmed, the caller receives failure and the last durable file can be uncertain. Never treat the model's prose alone as committed-state proof.
